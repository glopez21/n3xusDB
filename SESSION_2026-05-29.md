# Session: Deployment Architecture Redesign

**Date:** 2026-05-29

## Participants

- Developer (glopez21)

## Context

Discussion of deployment and connectivity strategy for SOC stack projects: LogSentry, AlertFlow, EventFlow, Augur, ThreatPulse, NetWatch, and others. The goal was to design a reliable, scalable architecture for connecting independent daemon tools to central hubs (Augur/ThreatPulse) across local and remote machines (AWS, Linode, LAN).

## Problem

The existing hub-and-spoke agent model (where `augur-client` bundled LogSentry+EventFlow+AlertFlow into a monolithic Augur agent) was failing due to:

- Tight coupling between components
- Dependency conflicts in a single venv/container
- Lifecycle management issues (restarting one component affected others)
- Brittle remote deployment

## Proposed Solution

Replace the monolithic agent approach with a three-layer architecture:

```
Daemon → n3xusDB (central buffer) → Omn1L1nk (delivery pipeline) → Augur/ThreatPulse (hubs)
```

### Layers

1. **Data Producers (daemons)** — LogSentry, EventFlow, AlertFlow, NetWatch run as standalone background processes. Each is independent, has its own lifecycle, and has no awareness of hubs.

2. **Data Buffer (n3xusDB)** — A centralized TimescaleDB instance with a unified `event_outbox` hypertable. All daemons write events here. Acts as a persistent queue — if hubs are down, events are not lost.

3. **Delivery Pipeline (Omn1L1nk)** — A single-purpose FastAPI service that polls `event_outbox`, enriches events via rules engine, and delivers to configured hubs (Augur, ThreatPulse, or both). Tracks delivery status, retries on failure.

4. **Hubs (Augur/ThreatPulse)** — No changes needed. They receive events from Omn1L1nk identically to how they received them from the old agent model.

### Write Paths

- **Local daemons** (same machine as n3xusDB): write directly to `event_outbox` via Unix socket — no HTTP hop, no auth needed, simplest path
- **Remote daemons** (AWS, Linode, LAN): HTTPS POST to Omn1L1nk's `/api/v1/ingest` endpoint. On network failure, fall back to a local SQLite buffer. The buffer is flushed on the next successful connection.

## Key Decisions

### Why not direct DB writes for remote machines?
PostgreSQL should never be exposed to the internet, even with TLS. The connector layer provides API key auth, validation, and a single attack surface.

### Why the single-event Augur endpoint (not batch)?
Augur's `POST /api/v1/events` runs the full pipeline (normalization, dedup, detection, UEBA, correlation, SIEM forwarding). The batch endpoint skips all of this. For a SOC, pipeline processing is more important than throughput.

### Why TimescaleDB for the outbox?
Already the planned engine for n3xusDB. Hypertables on `created_at` give automatic partitioning, compression, and retention for time-series event data.

### Why a new connector project (Omn1L1nk) instead of building this into Augur?
Omn1L1nk is hub-agnostic — it can route to Augur, ThreatPulse, or both simultaneously. It has its own deployment lifecycle, scaling needs, and failure modes. Keeping it separate prevents scope creep in Augur.

## Deployment Matrix

| Machine | Runs | Connects via |
|---------|------|-------------|
| Local (DB host) | n3xusDB, Omn1L1nk, Augur, ThreatPulse | Unix socket (DB), localhost (hubs) |
| Local (LAN) | LogSentry, EventFlow, AlertFlow daemons | Direct DB write or Omn1L1nk HTTP |
| AWS EC2 | LogSentry daemon | Omn1L1nk HTTPS + local SQLite fallback |
| Linode | LogSentry, AlertFlow daemons | Omn1L1nk HTTPS + local SQLite fallback |
| Future machines | Any daemon combo | Same as above |

## Omn1L1nk Feature Set

- **HTTP ingest** — `POST /api/v1/ingest` with API key auth, validates and writes to `event_outbox`
- **Poll loop** — background task polls unpushed events every 1-5s using `FOR UPDATE SKIP LOCKED`
- **Enrichment** — rule-based engine that escalates severity, adds confidence scores, appends tags, merges context
- **Routing** — delivers to Augur (single-event endpoint for full pipeline) and/or ThreatPulse
- **Delivery tracking** — marks events as pushed, increments attempts on failure, dead letter after N retries
- **Health** — `/health` endpoint with queue depth, delivery lag, error rate, hub status
- **Rule management** — CRUD API for enrichment rules stored in n3xusDB

## What Omn1L1nk Is NOT

- Not a database
- Not a hub/SIEM/SOAR
- Not a monitoring tool
- Not a replacement for Augur or ThreatPulse

## Augur Agent Model Change

Old model: daemon bundles `augur-client` → registers itself → pushes events directly to Augur API.

New model: Omn1L1nk registers and heartbeats daemons as agents on their behalf. Augur's Agents page shows each daemon instance as an individual agent (e.g., `LogSentry@aws-box-01`). The daemon never touches Augur's API.

This means:
- No `augur-client` dependency in daemon code
- No agent registration logic in daemons
- Centralized heartbeat management
- Augur API stays unchanged

## Implementation Session (Later same day)

### What was built

**n3xusDB** — Docker Compose + init script deployed:
- TimescaleDB container `n3xusdb` running on `127.0.0.1:5435`
- Databases created: `shared_db`, `augur_db`, `twn_db`, `eventflow_db`
- `shared_db` tables: `event_outbox` (hypertable), `daemon_api_keys`, `enrich_rules`
- `omn1l1nk_user` with read/write access to `event_outbox` only
- `shared_user` with INSERT-only access to `event_outbox` (for local daemon writes)

**Omn1L1nk** — Python/FastAPI service built and tested:
- `app/ingest/router.py` — `POST /api/v1/ingest` with API key auth via `daemon_api_keys` table, validates and writes to `event_outbox`
- `app/pipeline/poller.py` — Background loop polls `event_outbox` every 3s using `FOR UPDATE SKIP LOCKED`, delivers to `POST /api/v1/events` on Augur, tracks delivery_attempts and errors
- `app/pipeline/enrich.py` — Rule-based enrichment engine: severity escalation (only up, never down), confidence averaging (60% rule / 40% existing), tag appending, context merging; flattens nested YAML match rules for dot-notation field lookup
- `app/main.py` — FastAPI app with lifespan managing pool + poll loop, `GET /health` endpoint showing queue depth, delivery rate, error rate, hub statuses
- `app/config.py` — All config via env vars: `OMN1L1NK_DB_URL`, `OMN1L1NK_AUGUR_URL`, `OMN1L1NK_POLL_INTERVAL`, `OMN1L1NK_BATCH_SIZE`, `OMN1L1NK_MAX_RETRIES`
- `app/models/schemas.py` — Pydantic models for ingest/health/queue responses
- `app/db/session.py` — asyncpg connection pool wrapper

### Verified end-to-end

```
Daemon → POST /api/v1/ingest (201 Created) → event_outbox (pushed=FALSE)
→ poller picks up → enriches → tries POST /api/v1/events on Augur
→ Augur unreachable (not running) → delivery_attempts=1, error='delivery_failed'
→ /health shows queue_depth=1, augur_status='unreachable'
```

Expected behavior: events retry up to `max_retries` (5), then dead letter. No data loss.

### Fixes applied during build

1. TimescaleDB requires partition column (`created_at`) in unique indexes — used composite index `(created_at, id)` instead of PK on `id` alone
2. asyncpg JSONB adapter needs string input — `json.dumps()` on payload/context before INSERT
3. asyncpg returns JSONB as string when stored via `json.dumps()` — poller uses `json.loads()` to deserialize
4. Enrich match rules use nested YAML keys (`context.ip:`) — `_flatten()` converts nested dicts to dot-notation for `_get_nested()` lookup
